LOCALPILOT: EXACTLY 100 IMPLEMENTATION PROMPTS
Updated: 28 October 2026

HOW TO USE
Create a separate repository. Load the complete TXT handoff as project context,
or copy the numbered blueprint documents into docs/plan/. Give Antigravity ONE
numbered prompt at a time, in order. The sequence includes initial setup through
launch; earlier Prompt 0-8 examples in document 06 are superseded by this sequence.
Prompts are implementation tickets; complex tickets can require several sessions.
Exactly 100 prompts does not mean 100 automatic steps or a fixed delivery time.

COMMON INSTRUCTIONS APPLY TO EVERY PROMPT
Read the relevant plan sections and current repository instructions first. Inspect
existing work and continue it; do not recreate completed modules. Keep TypeScript
modular monolith boundaries and separate web/worker processes. Use Plus Jakarta
Sans/Inter, peach/orange tokens and accessible UI. All external writes require
server authorization, valid consent, current revision, capability and budget.
Never invent rankings, customers, provider success, data access or approval.
Do not expose secrets to client code, AI contexts, screenshots or logs. Respect
source-specific retention; derived data is not a loophole. Paid/live operations
stay gated until explicitly configured for an authorized test account and budget.
Do not damage an existing application or run destructive production migrations.
Deliver working behavior, meaningful verification and updated docs/progress.md.
Report changed files, commands/check results, screenshots for UI changes, and
externally blocked behavior. Mocks alone do not verify a real integration.
No whole-platform rewrite, arbitrary provider proxy or unbounded agent loops.

PHASE A: PROJECT AND SECURE FOUNDATIONS — PROMPTS 001-010

PROMPT 001 — Establish the project and implementation contract
Dependency: none; start in the new repository.
Read the full LocalPilot handoff and inspect the repository before changing it.
Create a concise product brief covering local-business onboarding, website/GBP,
content/social, rankings, competitor intelligence, citations and reputation.
Create docs/progress.md with 100 numbered ticket slots, implemented/verified/
externally-blocked states, and evidence links. Record assumptions about India-first
launch, business vertical and branding. Document that private Outrank UI was not
inspected. Deliver a scoped repository plan and a safe initial structure, without
generating every module. Acceptance: the next ticket and scope boundaries are clear.

PROMPT 002 — Validate external capabilities before building against them
Dependency: 001.
Create an integration feasibility register using current primary documentation:
GBP eligibility/access/consent/storage, Meta login routes/permissions, WordPress,
GSC, ranking coordinates and payment eligibility. Record verified date, required
owner action, approval state, supported actions, version and fallback. Prepare
application/review checklists without submitting or spending through unidentified
accounts. Recheck any price before incorporating it. Acceptance: unavailable
capabilities are explicitly blocked rather than simulated as working; uncertainty
around review automation and historical GBP data has an assigned decision owner.

PROMPT 003 — Record architecture decisions and module boundaries
Dependency: 001-002.
Write ADRs for TypeScript/Next.js, managed PostgreSQL/auth, Drizzle migrations,

location ownership and internal modules for intelligence and reviews. Validate
queue privileges/connection mode in a minimal spike before committing to the
library. Acceptance: chosen versions and alternatives are justified, modules
cannot bypass domain permissions, and no unnecessary microservice is introduced.

PROMPT 004 — Scaffold the workspace and quality commands
