# Product definition and Outrank analysis

## 1. What to build

LocalPilot is a multi-tenant SaaS that takes a local business from fragmented online accounts to a consistent, measurable marketing workflow. An owner supplies a URL or business details, confirms facts, connects accounts, chooses a goal and spend limit, reviews a month of planned activity, and approves an automation policy. The product then generates, schedules, publishes, checks outcomes, and proposes improvements.

The main product outcome is **qualified enquiries and a maintained local presence**. Published-content counts and internal health scores are operational metrics. They must not be represented as proof of ranking improvements.

Initial assumptions: India-first; English first, Hindi after quality validation; one location per starter subscription; agencies later; existing WordPress sites plus a template-based hosted site. Preserve country, currency, IANA timezone, language, address format, phone format, and tax configuration in the model from the start.

The cheapest useful product is not daily AI articles plus unlimited integrations. It is one accurate business record, a useful calendar, reliable publication to a small number of channels, weekly visibility measurement, and clear owner actions when automation is blocked.

### What cannot be claimed from this research

- Outrank's database, AI vendors, queues, prompts, and infrastructure were not verified.
- Its marketing performance claims do not establish what another product will achieve.
- The public pages reviewed do not establish a complete native GBP/local-grid/social/citation product. Those are proposed additions here, not verified missing features across its private product.

## 3. Local SEO requires a different product model

Keep four measurements separate:

1. **Website search performance:** GSC clicks, impressions, CTR, average position by available query/page/device/country. This is observed search analytics, not an exact coordinate-based local rank.
2. **Google Maps visibility:** a sampled rank for a keyword at a defined coordinate, language, device, time, and result depth. There is no single universal business rank.
3. **Business Profile performance:** the metrics exposed by the current GBP Performance API. A website click or call-button interaction is not automatically a verified lead or completed call.
4. **Conversions:** hosted-form enquiries, owner-confirmed leads, and optionally analytics events. Do not add clicks, directions, and enquiries into a misleading total.

Google describes local ranking through relevance, distance, and prominence/popularity; a product cannot purchase or guarantee a better local rank. Show the factors the software can influence and the measurements it actually has. [Google local ranking guidance](https://support.google.com/business/answer/7091?hl=en).

## 4. Automation feasibility and boundaries

| Task | Practical automation | Boundary and product behavior |
|---|---|---|
| Import business facts | Crawl authorized public site and import user data | Owner confirms conflicts before facts become authoritative |
| Build website | Generate structured sections from confirmed facts | Owner supplies domain/DNS access and publishes first version |
| Connect GBP | OAuth + list authorized locations | API project approval, owner access, and eligibility required |
| Create/verify GBP | Guided setup and supported API steps where available | Owner action required; no automatic bypass of verification |
| GBP posts | Queue supported post types for eligible locations | Respect category restrictions, express consent, API availability |
| GBP identity edits | Generate before/after proposal | Explicit approval per sensitive change; no automatic name stuffing |
| GBP review replies | Draft from current authorized data | Consent required; negative/sensitive replies always reviewed |
| Instagram publishing | Supported professional-account media via approved integration | Personal accounts unsupported; conversion/reconnect guidance |
| Facebook publishing | Authorized business Pages | Personal-profile posting is outside the scope |
| Blog publishing | WordPress connector or hosted renderer | CMS permissions and ownership required |
| robots.txt fixes | Full control on hosted sites; signed plugin support on WordPress | External CMS may only allow recommendations or export |
| Citation submissions | Directory API/partner where available; prepared submission packets elsewhere | Directory ownership, OTP, moderation, and payment can need owner work |
| Rankings | Paid SERP provider and geo-grid sampling | Meter usage; disclose freshness, depth, failed points |
| Indexing | Sitemap, internal linking, indexing diagnostics | No guaranteed Google inclusion or instant index button |
| AI visibility | Repeatable sampled prompts through named providers | API responses are not identical to consumer app recommendations |

GBP API access is an early launch dependency: Google's current prerequisites include an active, verified profile managed for 60+ days and a representing website. Start the access request before building the whole integration. [GBP prerequisites](https://developers.google.com/my-business/content/prereqs).

GBP-specific consent, storage and downstream access rules shape implementation: do not expose the platform's Google project as a generic scripting proxy; preserve specific express consent; make disconnection easy; build a source-specific retention policy. Treat ambiguity about recurring action consent or data retention as a release gate for that feature. [GBP API policies](https://developers.google.com/my-business/content/policies).

Instagram has distinct Instagram Login and Facebook Login products. The Facebook Login route requires a linked Page; the Instagram Login route must be validated separately. Select one route per adapter and never mix its scope names or tokens. Public SaaS access depends on the permissions approved for that app. [Meta-maintained Instagram collection](https://www.postman.com/meta/instagram/documentation/6yqw8pt/instagram-api). Direct Meta documentation was rate-limited during research, so exact permission/version checks remain a Phase 0 task.

## 5. Product modules and requirements

### 5.1 Business setup and source of truth

Required fields: legal/display business name, category, services, country, public or hidden address mode, service area, phone, website, hours, timezone, booking/contact destination, owner contact. Optional fields: pricing bands, credentials, team, languages, brand voice, approved offers, real photos, service exclusions and prohibited claims.

Each fact needs a provenance record: source type, URL or user input, captured time, confidence, verification status, owner confirmation time, and applicable location. Example conflict: site says 9am opening, GBP says 10am. Show both and ask the owner to resolve it; do not silently overwrite GBP.

Maintain versions. A new phone number invalidates future content variants containing the old number. Content already published is placed in a reviewable correction queue. A business with a hidden service-area address must not have its private address inserted into generated pages or public structured data.

### 5.2 Onboarding flow

1. Google/email sign-in and organization creation.
2. Choose existing website, existing GBP, or starting from scratch.
3. Import optional website details and connect accounts independently.
4. Select one business/location; avoid accidentally connecting every location in an account.
5. Confirm facts, photos, target area, services, voice and conversion goal.
6. Show initial site audit and a rank scan estimate before spending credits.
7. Generate a 30-day proposed plan; let the owner remove topics and offers.
8. Configure review-first mode; offer channel-specific automation after first successful publication.
9. Start baseline jobs asynchronously and show resumable progress.

Each integration can be skipped. A GBP-only business can still use planning and GBP publication while creating a website. A website-only business can use blogs and GSC. Show which capabilities are available, blocked, unapproved, disconnected, and unsupported.

Activation target: confirmed facts, one connected or hosted destination, baseline requested, one content item approved, and automation policy selected. Measure actual time; target under 15 minutes excluding verification/DNS wait.

### 5.3 Local keyword research and strategy

Inputs: services, accepted locations, seasonality, customer questions, existing pages, actual GSC queries, and measured competitor samples. Distinguish provider-supplied volume from AI-suggested topics. Never invent volume or difficulty values.

Cluster by intent: immediate service demand, service comparison, price explanation, maintenance/advice, local proof, and booking FAQs. Map each cluster to an existing or proposed canonical URL. Detect cannibalization before creating a new blog or service page.

Use a transparent prioritization heuristic: relevance 35%, conversion fit 25%, current visibility gap 20%, competition opportunity 10%, seasonality 10%. This is an internal planning score, not a Google metric. Label missing inputs and renormalize only after explaining which fields are excluded.

Initial cadence: 4–8 useful blogs/month and 8–12 campaign ideas; derive channel variants from those ideas plus genuine business updates. Adjust to the business; do not generate 30 thin articles merely to fill dates.

### 5.4 Content studio

Pipeline: brief → outline → draft → facts/claims validation → assets → channel variants → deterministic checks → review/approval → scheduled publication → reconciliation.

Editor must support headings, links, images, alt text, lists, excerpts, title/meta, canonical URL, slug, channel preview, revision history and restore. An AI edit creates a new revision and shows a diff. Publishing freezes a revision; later edits invalidate its approval until reviewed or covered by an eligible policy.

Content model: one campaign idea can produce a blog, a concise GBP update, an Instagram image/caption, and a Facebook post. Each is independently editable and independently succeeds/fails. A campaign does not need a blog to exist. For a blog-derived campaign, wait for the verified published URL before finalizing link variants.

Quality rules: grounded service availability and hours; no invented local projects, reviews, staff or certifications; no fabricated pricing; no unsupported superiority claims; no fake before/after images. AI-generated graphics can illustrate a topic, while real-business portfolio posts use approved real photos.

### 5.5 Calendar and automation center

Month/week/list calendar; filters for location, channel, status and owner. Drag/reschedule changes due time and recalculates approvals if payload changes. Local timezone shown prominently. Include blackout dates, holidays, quiet periods, duplicate-topic detection, collision checks, quotas, and an immediate pause button.

Automation policies are versioned per location/channel/action. Example: publish approved seasonal maintenance tips twice weekly, at most eight monthly, using approved services/photos and a set spend cap. Policy excludes offers with new prices and sensitive claims. Record scope, cadence, allowed categories, approving user, consent text, timestamps and revocation.

Do not treat one generic signup checkbox as permission for all account edits. Default recurring GBP behavior to review until the integration owner verifies that the implemented consent flow meets Google's current requirements.

### 5.6 Rankings and competitors

Start with five keywords, a 3×3 grid, weekly scans, top-20 display depth, and provider configuration verified in a technical spike. A point stores coordinate, request parameters, status, observed rank or not-found-within-depth, timestamp and source.

Competitors are recognized by stable identifiers where provided, rather than name alone. Owner confirms ambiguous target matches. Keep business listings from competitor/SERP providers separated from owner-authorized GBP account data.

Show grid, top-3 coverage, per-keyword history, and competitor share across the same successful points. Definitions and censoring are in the architecture document. Do not compare scans with different grid footprints as if they were equivalent.

### 5.7 Technical website SEO

Audit HTML status, indexability, canonical links, robots, sitemap contents, title/meta, headings, broken links, internal links, mobile usability, structured data, image size, and performance samples. An internal score must have inspectable weighted checks, not an unexplained AI number.

Hosted sites can receive validated automatic fixes within policy. External sites receive a patch proposal, plugin-supported change, or manual instructions. Preview → approval → snapshot → publish → verify → rollback is mandatory for robots, redirects, canonical and site-wide indexing changes.

robots.txt controls crawler access; it is not a reliable removal mechanism or security boundary. Google does not support `noindex` inside robots.txt. Use supported tags/headers and allow crawlers to read them where appropriate. [robots guidance](https://developers.google.com/search/docs/crawling-indexing/robots/intro), [noindex guidance](https://developers.google.com/search/docs/crawling-indexing/block-indexing).

Ordinary blogs/service pages should use sitemaps and useful internal links. Google's Indexing API is restricted to supported job-posting/live-stream pages. [Indexing API scope](https://developers.google.com/search/apis/indexing-api/v3/using-api).

### 5.8 Website creation

Three templates initially: service professional, appointment business, and local storefront. Structured blocks: hero, services, service detail, about, team, gallery, verified testimonials, FAQs, contact, hours, location/service area, booking link, blog, privacy/contact disclosures.

Owner can edit text, reorder permitted blocks, choose approved imagery and theme, and preview mobile. Hosting supports platform subdomain first, then verified custom domain and managed HTTPS. A domain is bought from a registrar; 'custom domain included' means connection support unless domain registration is explicitly sold.

Avoid a freeform page builder, ecommerce, complex booking engine, or arbitrary tenant JavaScript in the first release. Link existing booking tools. Contact forms need abuse limits, honeypots, optional challenge, delivery status and lead export.

### 5.9 Citations and reputation

Separate a citation (business listing/name-address-phone mention) from a backlink and from an AI citation. Use an authoritative NAP record, country/category-specific directory catalog, claimed status, field comparison, evidence URL, last checked time and owner task.

Statuses: discovered → mismatch/missing → prepared → owner verification → submitted → live verified → update required/rejected. Submitted never means live. Verification checks business identity and fields, with uncertain matches assigned for review.

Begin with 10–20 relevant directories for the target country/vertical, not '100 guaranteed submissions'. Each directory records supported method, permitted automation, fee, credentials/ownership requirements, and update/delete process. Directory APIs or a fulfillment partner come later; do not build CAPTCHA bypasses.

Review features: unified current inbox, AI drafts, owner approval, reply status, neutral review-request link/QR, opt-out handling. Do not generate customer reviews or selectively request reviews only from happy customers. Customer outreach by email/SMS requires a separate product consent and legal review for the launch market.

### 5.10 Reporting, billing, and agency expansion

Owner dashboard shows completed work, pending actions, actual measured visibility, enquiries, and cost/usage. Reports compare matched periods, use source-specific dates, show missing data, and distinguish correlation from attribution.

Pricing is per active location with included quotas. Billing includes subscription state, grace period, credit ledger, prepaid overages, invoices and cancellation. Cancellation pauses future paid actions, preserves agreed read/export access, and does not delete an owner website without a clear hosting policy and notice.

Agency release adds location groups, delegated roles, approval ownership, white-label report styling, bulk actions with per-location results, and account isolation. The tenancy model supports this from day one; the agency interface is deferred.

## 7. Success measurements

Track activation rate, time to first verified publish, integration success/reconnect rates, percentage of jobs completed without owner repair, review workload, content approval rate, per-location variable cost, support time, retained paid locations and owner-confirmed enquiries.

Suggested beta gates: 10 pilot locations, 3 business categories tested, 2 weeks of scheduled publication with no duplicate external posts, all tenant-isolation tests passing, successful backup restoration, understandable failure states, and demonstrated owner value. Ranking growth is observed over appropriate periods; never use it as a guaranteed engineering acceptance condition.

# Architecture and engineering specification

Everything below is a proposed architecture for LocalPilot, not a claim about Outrank's implementation.

## 1. System structure

Use a modular monolith with independently running web and worker processes. One repository, one migration history, one shared contract library. Split services only when measured workloads or team ownership justify it.

```mermaid
flowchart LR
  Owner[Owner / agency browser] --> Web[Next.js application]
  Visitor[Business website visitor] --> Site[Hosted site renderer]
  Web --> Auth[Managed authentication]
  Web --> DB[(PostgreSQL)]
  Web --> Storage[Object storage]
  Site --> DB
  Site --> Storage
  DB --> Jobs[Durable jobs / outbox]
  Jobs --> Worker[Node worker]
  Worker --> AI[Gemini adapter]
  Worker --> Rank[SERP provider adapter]
  Worker --> CMS[WordPress / hosted publisher]
  Worker --> GBP[GBP APIs]
  Worker --> Meta[Instagram / Facebook APIs]
  Worker --> DB
  Worker --> Storage
  Providers[Provider webhooks] --> Inbox[Verified webhook inbox]
  Inbox --> DB
```

### Selected stack

| Layer | Initial choice | Reason / constraint |
|---|---|---|
| Language | TypeScript throughout | Shared types and fewer AI-generated integration mismatches |
| Web | Current stable supported Next.js + React | SSR marketing, dashboard and hosted pages in one codebase |
| UI | Tailwind, accessible Radix/shadcn-style primitives, Lucide | Fast composition; theme through centralized tokens |
| Client state | TanStack Query for remote jobs/data; local state for forms | Avoid a global store for every API response |
| Forms/contracts | React Hook Form + Zod | Shared validation; explicit server-side authorization |
| Data/auth | Supabase PostgreSQL/Auth initially | Managed identity, relational data and backup options |
| ORM | Drizzle; SQL migrations for constraints/RLS | Transparent SQL and low worker overhead |
| Queue | pg-boss or an equivalently proven PostgreSQL job library | No Redis bill at launch; separate job schema and least-privilege role |
| Editor | TipTap with restricted extensions | Structured content, revisions, safe renderers |
| Storage | S3-compatible R2 | Media, generated assets, audit artifacts with source-specific retention |
| Analytics UI | Recharts or equivalent; tables before exotic charts | Owner-friendly charts; accessible tabular alternatives |
| Maps | Grid-only visualization first; MapLibre with licensed tile source later | Ranking API and basemap licensing are separate costs |
| Hosting | Containerized web/worker on a small VM | Long-running work and scheduling fit conventional workers |
| Tests | Vitest, integration DB tests, Playwright E2E | Focus on real failure and permission boundaries |

At Phase 0, pin exact compatible versions and commit lockfiles. Verify queue-library PostgreSQL requirements and privileges against the managed database; do not discover this after building jobs around an unsupported configuration. Use a supported direct/session connection for long-running workers, not a transaction pooler that breaks library assumptions.

Cheapest cash variant: PostgreSQL and authentication hosting can be self-managed, but do not write a custom identity system. Use a maintained auth library with secure session defaults. The recommended route spends more on managed identity/database to reduce launch risk and maintenance.

## 2. Tenant model and authorization

Organization owns membership and billing. Business owns shared branding and facts. Location owns local facts, profiles, keyword tracking, campaigns and quotas. A single-location business still gets a location record. Every tenant-owned object has `organization_id`; location-bound data also has `location_id`.

Roles: owner (billing, deletion, all permissions), admin (business/integrations/policies), editor (draft and submit), approver (approve scoped content), analyst (read/report), billing manager (financial access), platform operator (separate internal capability).

Permission checks are capabilities plus resource scope, not just role strings. Example: `content:approve` for location A does not grant approval at B. Membership is checked server-side against the authenticated user. Ignore any organization ID supplied as proof of access by the browser.

Use RLS for client-accessible data and tenant-safe server repositories. Use composite foreign keys or equivalent validated constraints to prevent linking a campaign from one organization to another organization's location. Public site read access is limited to published projections, never draft tables.

Workers use an internal role but require explicit organization/location context for each job. Do not run arbitrary user-selected SQL through privileged connections. Cache keys, job keys, object paths and logs include tenant scope. Automated cross-tenant negative tests cover reads, writes, exports, signed URLs and background jobs.

### Important uniqueness and indexing

- Membership unique on organization/user.
- Integration asset unique on organization/provider/external asset ID.
- Domain host globally unique among active claims; domain ownership must be verified before routing.
- Content revision unique on content item/revision number.
- Publication unique on variant revision/destination/scheduled occurrence.
- Webhook event unique on provider/event ID, with payload digest fallback where necessary.
- Credit ledger operation unique on organization/idempotency key/operation type.

### Retention is source-specific

Do not apply a universal 12-month retention rule to Google/provider data. The current GBP API policy limits temporary storage of API content and restricts manipulation/aggregation. Separate owner-entered facts, owner-authored content, GSC records, paid SERP data, and GBP API content into different retention classes. Default GBP content expiry to at most 30 calendar days, including derived copies and operational logs where applicable; confirm the intended reporting use before shipping persistent GBP history. Do not persist lifetime review text or derived long-term GBP trend aggregates without a permitted basis. Backups containing restricted data need corresponding expiry controls; restoring a backup must replay deletion/expiry records before serving data.

Source: [GBP storage and API policies](https://developers.google.com/my-business/content/policies). Assign an engineering owner to resolve permitted historical reporting and backup handling with the provider; gate affected features until resolved.

## 4. Job execution and publication correctness

### Content state

`idea → brief_ready → generating → draft → checks_failed | needs_review → approved → scheduled → publishing → published`

Additional states: `generation_failed`, `cancelled`, `superseded`. Channel variants and publications have their own states. One failed social destination does not roll back a successful blog.

### Execution sequence

1. Authorize the action and check entitlement.
2. In one DB transaction, create the command, reserve a bounded credit amount, and write an outbox event.
3. Dispatcher enqueues the outbox event with a stable unique job ID; replay is safe.
4. Worker leases the job, reloads current resource state, and checks consent, cancellation, pause, facts version and available token capability.
5. Generate or publish using a provider adapter; persist each meaningful checkpoint.
6. Reconcile result using external IDs or a safe provider-supported lookup.
7. Finalize usage, release unused reservation, update state and notify if actionable.

Design for **at-least-once jobs**. Do not promise exactly-once external side effects. Providers can time out after accepting a post. Mark ambiguous attempts `unknown_outcome`, reconcile first, and never blindly repost. If external lookup cannot resolve it, put it in owner/operator review.

Retry transient network/429/5xx failures with capped exponential backoff and jitter; obey provider retry headers. Authentication/permission errors switch to reconnect/approval states. Validation errors go to repair. Example policy: 1m, 5m, 20m, 1h, 4h, then dead-letter; adapter-specific limits override. A job can be cancelled between steps, but already accepted external writes require a separate compensating action.

An approval binds the exact payload revision, facts version, destination and policy. Before dispatch, a revision/hash mismatch blocks publication. Lock or compare-and-swap the scheduled occurrence so two workers cannot create separate active publication attempts.

### Scheduling

Store user-intended local schedule, IANA timezone, recurrence rule, resolved UTC occurrence and schedule revision. Resolve future occurrences explicitly around DST gaps/duplicates. India has no seasonal DST, but the product model supports other countries. Generate occurrences ahead, select due jobs every minute, and recover missed runs after worker downtime. Mark overdue items and apply an explicit catch-up policy; do not dump a week's social posts at once.

### Queue lanes and fairness

Priorities: due publication, token refresh, reconciliation, draft generation, rank scans, audits, maintenance. Apply per-provider and per-tenant concurrency so one agency cannot exhaust the queue. Initial conservative worker concurrency: 2 AI calls, 1 crawl domain at a time, 2 publication operations per provider account; tune with measurements. Run browser-based audits in a capped separate process to avoid exhausting web memory.

## 5. Provider adapter contracts

```ts
type Capability = {
  action: string;
  supported: boolean;
  reason?: string;
  checkedAt: string;
};

interface PublishingAdapter {
  capabilities(connectionId: string): Promise<Capability[]>;
  validate(payload: unknown): Promise<{ valid: boolean; issues: string[] }>;
  publish(command: {
    publicationId: string;
    approvedRevisionId: string;
    connectionId: string;
  }): Promise<{
    state: "accepted" | "published" | "pending" | "unknown_outcome";
    externalId?: string;
    externalUrl?: string;
  }>;
  reconcile(publicationId: string): Promise<unknown>;
}
```

The adapter loads server-side payload and credentials; browsers never send arbitrary provider tokens or external target IDs as authority. Keep capabilities by action and media type; account connected does not imply every publish format is allowed.

### Google Business Profile

Use approved project, OAuth and explicit location selection. Separate account management, business information, performance, posts/reviews and verification surfaces; they do not all share one version/base URL. Verify currently supported operations in a spike. Do not assume historical endpoint examples still work.

Record scopes, selected locations and last capability check. Before profile edits show a field diff and obtain appropriate consent. Never revert Google edits automatically. No generic developer endpoint that forwards arbitrary GBP calls through the platform's credentials. An owner can disconnect and revoke future actions immediately; complete provider disassociation according to policy.

### Meta

Separate Instagram Login tokens/scopes from Facebook Login flows. Facebook Page publishing uses selected authorized Pages. Instagram requires eligible professional accounts. Implement media validation, upload/container creation, readiness polling, publish, and external-ID reconciliation. Stage publicly retrievable media only for the necessary provider fetch window; preview assets remain private. Tokens can be revoked without expiry, so handle auth errors, not just dates. Version the Graph API configuration and track deprecation dates.

### WordPress

Fast path: HTTPS REST API with owner-created application password stored encrypted. Validate user capability and target site identity. Upload media, create/update posts, preserve external post ID and verify the resulting URL. Standard WordPress REST publishing does not guarantee edits to SEO-plugin metadata or root robots.txt; add a narrowly scoped signed companion plugin later for supported technical fixes. Do not request administrator passwords.

Companion plugin, if built: signed timestamped commands, rotating shared secret, allowlisted actions, replay prevention, exact capability checks, diagnostics, version negotiation, backup/diff/restore and uninstall cleanup. Never implement arbitrary PHP execution or filesystem writes.

### Hosted sites

Render structured, sanitized content through trusted templates. Tenant preview requires signed auth and `noindex`, but also actual access control. Public published pages use tenant-aware caches keyed by verified host/site/revision. Reject unknown hosts; never trust raw forwarded-host headers. Domain claim → DNS ownership check → route allocation → TLS issuance → health check → active. DNS/TLS failures are visible recoverable states. Prevent dangling custom-domain takeovers on cancellation and reassignment.

### Ranking provider

Validate geocoordinate behavior, result identity, depth, language/device parameters and costs with a sample before building a map. Keep queued task IDs; poll with bounds or validate callback destinations. Some provider task errors arrive inside a successful HTTP response; inspect task-level status. Treat failed/no-results/not-found distinctly.

## 6. Ranking definitions

Recommended default display depth: 20; record actual provider depth separately if it returns 100. Match target by reliable provider identifiers, then confirmed URL/address fallbacks. Name similarity alone cannot establish identity.

For a scan with N successfully observed points:

- Top-3 coverage = points ranked 1–3 / N × 100.
- Found-point average rank = sum of observed ranks / found points; always display found-point count.
- Optional capped rank = use 21 for not found within top 20, clearly labeled as a calculated score, never raw rank.
- Error points are excluded from rank metrics and shown as missing; zero successful points produces 'scan unavailable', not 0% visibility.
- Top-3 share among tracked businesses = each tracked business's top-3 appearances divided by all tracked appearances, with definition visible. It is not total market share.
- Compare identical keyword, grid/config version, depth, device and locale; otherwise explain incompatibility.

Each rank run stores configuration hash, successful/failed points and source timestamp. A lower numerical rank is improvement; a rank of 0 is invalid. A 3×3 grid is a geographic sample, not coverage of all searches in a city.

## 7. AI architecture and quality controls

Use an internal `TextGenerator` and `ImageGenerator` provider interface with configuration aliases (`text_economy`, `text_quality`, `image_economy`). Persist actual provider/model version. No uncontrolled autonomous agent loop is needed for scheduled publication.

Retrieve confirmed business facts and selected source excerpts. Start with PostgreSQL full-text retrieval and structured fact lookup; use embeddings only after a measured retrieval problem. A vector database is unnecessary for ten service pages per business.

Prompts return validated schemas: brief, outline, article blocks, channel variants and a claims manifest. Each business-specific claim references a fact ID or supporting source. Deterministic checks verify names, NAP, hours, links, required disclosures, forbidden claims, media sizes, duplicate topics, unsafe HTML and quota. AI critique adds a signal; it is not proof of factual accuracy.

Keep web pages and user uploads as untrusted content. Extracted text cannot grant tool permissions, change prompts, access other tenants, or authorize account writes. The generator has no direct publish credentials. Limit retrieval size, output length, tool use and attempts.

Evaluation dataset: at least 30 examples across chosen categories, including hidden address, price absent, closed days, multilingual names, misleading source text, conflicting hours, and negative review sensitivity. Score factual correctness, prohibited-claim avoidance, usefulness, repetition, tone, cost and approval rate. Upgrade the model for complex content only when evaluation data warrants it.

## 8. HTTP contracts and client behavior

Use REST route handlers with generated or shared schema definitions. Return commands asynchronously with `202 {jobId, resourceId, statusUrl}`. Poll at a modest interval, pause in background tabs, and back off; realtime infrastructure is optional.

Suggested routes:

Every mutation validates tenant authorization, version, entitlement and idempotency key as applicable. Return standardized error codes such as `RECONNECT_REQUIRED`, `APPROVAL_REQUIRED`, `QUOTA_EXCEEDED`, `REVISION_CONFLICT`, `PROVIDER_PENDING`, `UNSUPPORTED_ACTION`. Owner-facing messages explain next steps without leaking provider secrets.

## 9. Security, privacy and abuse controls

- Secure HttpOnly session cookies; CSRF protection for cookie-authenticated mutations; OAuth state and PKCE where supported.
- Envelope encryption for refresh/access tokens; secrets outside source control; key version and tested rotation.
- Verify webhook signatures against raw bodies; deduplicate and durably acknowledge before work.
- Crawl/import URLs must block loopback/private/link-local/cloud-metadata addresses and unsafe schemes, revalidate redirects/DNS, cap response sizes/time, and prevent DNS rebinding. Disable arbitrary authenticated crawling.
- Sanitize rich content and SVG; verify uploads by MIME/signature, size and image decoding; strip unnecessary metadata.
- Rate limit login, imports, preview links, forms, exports and generation. Use storage quotas and per-tenant spend caps.
- No credentials in frontend env vars, logs, AI prompts, analytics or user exports.
- Owner deletion/export/disconnect workflow; audit privileged access; separate operator role; require reason for support access.
- Source-specific deletion cascades across caches, derivative data, object storage and backups according to applicable terms.
- Jurisdiction-specific privacy, billing and messaging review before public launch. This blueprint is not a legal determination.

## 10. Deployment, operations and scaling

Start with production and staging environments; isolated database/auth projects and provider test assets where possible. Develop on local containers. Use CI to run lint/types, domain tests, DB migrations and critical E2E; build containers in CI so a small production VM does not compile the app.

Deploy versioned images behind Caddy/Nginx with HTTPS. Health endpoints distinguish liveness, DB readiness and worker heartbeat. Expand-and-contract migrations; back up before destructive changes; app rollback must be compatible with the deployed schema. Use runtime flags for each provider capability and a global outbound-action kill switch.

Observe: queue age, overdue publications, failure/retry rate, unknown outcomes, token failures, scan point failures, AI dollars per approved article, credits reserved but not finalized, webhook lag, storage growth, DB connections, memory and slow queries. Alerts should require action; routine success can go into a daily digest.

Recovery goals for beta: target RPO ≤24h and RTO ≤8h for customer-authored data, backed by a restore drill. Managed daily backups are not proof of recoverability; maintain encrypted off-site exports consistent with retention rules. Test restoration, key access, domain routing and scheduler deduplication. Distinguish these targets from a contractual SLA.

Scale when measured: split web/worker resources when heavy jobs affect latency; move DB compute when connections/IO require it; partition high-volume rank data when queries warrant it; add worker lanes for expensive crawls. At 1,000 locations × 20 keywords × 25 points × 4 scans, there are 2 million point observations/month, so establish retention/downsampling and provider rights before reaching that scale. No Kubernetes or microservices are required simply because the product is a SaaS.

- Domain ownership is verified before routing; expired/cancelled domain claims cannot be hijacked.
- Forms have abuse controls and observable delivery.
- Robots/canonical/redirect changes support preview, approval, verification and rollback.
- Rendered public HTML contains content/metadata without requiring client execution.
- Sitemap lists only published canonical URLs; 404s and redirects use correct status codes.

## Phase 6 — GBP and Meta publishing (2–3 weeks; approval-dependent)

Implement selected-asset OAuth connections, capability registry, consent UI, explicit field diffs, eligible GBP post publishing, current performance reads subject to policy, Facebook Page posts and Instagram supported image publishing. Defer reels/stories until basic image publishing is reliable. Implement disconnect/reconnect, media processing, signature validation, notification inbox and provider reconciliation.

Gate:

- Approved app works for an external pilot owner's selected assets, not only developer-role assets.
- Actual scopes and token routes match official current requirements.
- Owner-specific consent is recorded and enforced immediately before dispatch.
- Expired/revoked tokens produce an actionable reconnect state.
- One campaign can have blog success and Instagram failure without duplicate blog publication.
- Provider-supplied content retention/deletion jobs work, including logs and backups as required.
- Unsupported categories/formats are blocked with an explanation.

Do not claim this phase is done while app review is pending. If blocked, continue website/ranking/content beta and label channel publishing unavailable.

## Phase 7 — citations, billing and paid-beta hardening (1–2 weeks)

Implement directory catalog, NAP checks, prepared submission packet, owner verification tasks and evidence of live listings. No universal automatic-submission claim. Add subscription integration, per-location entitlements, atomic allowance/credit ledger, usage page, spending limits, grace periods, cancellation and exports. Payment processor selection is confirmed in Phase 0; provider fee rate is configuration, not hardcoded.

Gate:

- Submitted citation cannot count as verified live without evidence.
- Duplicate/out-of-order billing webhooks do not double-credit or incorrectly reactivate a cancelled plan.
- Plan changes and time-window resets preserve ledger correctness.
- Overage is disabled unless explicitly enabled/prepaid.
- Trial abuse cannot create unlimited AI/rank jobs.
- End-to-end support runbooks, kill switch, metrics and alerts are operational.
- Restore drill completed; documented RPO/RTO targets supported by evidence.

Phases 0–7 collectively form the approximately 12–18 week engineering envelope. Do not sum each minimum as an external-approval promise; some UI/spike work overlaps, while unpredictable review waits do not disappear.

## Phase 8 — optimization and reputation (2–4 additional weeks)

Add review reply drafts/approval, neutral review links, lawful outreach only if enabled, content performance candidates, revision comparison and controlled republishing. Refreshes preserve external IDs, slugs, valuable links and owner changes. Add a cooldown and minimum-data threshold before suggesting updates. Validate Hindi generation with reviewers if introducing it.

Gate: candidate selection shows source data and uncertainty; updates cannot erase custom content; owner may reject/restore; no invented attribution or reviews; provider-specific current retention policies still apply.

## Phase 9 — agencies and scale (3–6 additional weeks)

Build scoped team/location groups, bulk policy application with per-location results, agency usage allocation, report branding, partner citation fulfillment, optional more CMS adapters and operational scaling. Add advanced onboarding only after single-location activation is sound.

Gate: bulk actions preserve consent/permissions per location, agency users cannot cross client scopes, queued work is fair, billing reconciles by active locations and measured credits, and load tests meet measured workload targets.

Optional AI-visibility tracking and weekly tool generation need separate evaluation, budgets and product validation. They are not dependencies of a useful local-business launch.

## 2. Engineering task sizing and productivity

Each implementation ticket should fit 0.5–2 development days and contain: owner problem, route/UI entry, schema change, permission requirement, state transitions, provider contract, failure cases, acceptance evidence and migration/rollback notes.

Example ticket: 'Schedule an approved WordPress article'. Scope includes immutable revision, destination authorization, timezone conversion, idempotent command, quota reservation, queued state and verification URL. It excludes AI generation, social publication and billing UI. This prevents a coding agent from implementing shallow versions of six modules simultaneously.

Maintain a progress file with states planned/in-progress/implemented/verified/externally blocked. A screen that works only with fixtures is implemented visually, not verified functionally. Review generated migrations and dependencies before merging. Prefer one editor, one form library and one provider adapter pattern.

## 3. Meaningful testing strategy

| Risk | Required evidence |
|---|---|
| Tenant leakage | DB/RLS/API/asset negative tests with two organizations |
| Duplicate posts | Worker crash, retry, duplicate command, timeout and reconciliation scenarios |
| Unauthorized publishing | Role, consent revision, resource edit, disconnect and pause tests |
| Wrong costs | Parallel reservations, repeated webhook, cancelled job, failed attempt and reset tests |
| Wrong ranks | Failed/missing/censored observations; identity ambiguity; comparison compatibility |
| Website damage | Host isolation, draft leak, robots diff and rollback, domain takeover scenario |
| Untrusted crawl | Private IP/redirect/DNS/oversize payload protections |
| Bad generated claims | Evaluation fixture set and human spot review |
| Broken integration | Contract fixtures plus a minimal real authorized end-to-end run |
| UI regressions | Key viewport screenshot comparison and accessibility checks |
| Recovery | Restore DB, keys, media references and resume schedules without duplicates |

Do not spend the initial budget testing every presentational wrapper. Prioritize the cases that could post the wrong content, expose a tenant, bill incorrectly, or break a customer website.

## 4. Launch pilot and release checklist

Pilot with 5–10 businesses. Week one: owner onboarding, fact confirmation, one reviewed campaign and rank baseline. Week two: scheduled activity and failure handling. Subsequent weeks: usefulness, owner time saved, actual enquiries, content approval rate and operating costs. SEO outcomes need longer observation than a two-week operational pilot.

Before charging for a feature: published scope matches working capabilities; pricing includes actual quotas; terms/privacy/contact and deletion flows exist; provider approvals valid; billing reconciled; no duplicate publication under retry; no demo data in live screens; production/staging isolated; alert routing and restore evidence exist; support owner assigned; deployment rollback tested.

## 5. Release risk register

| Risk | Mitigation / release decision |
|---|---|
| GBP eligibility/review delay | Apply immediately; ship website/content/rank path independently |
| Meta permission/review failure | Keep export/manual delivery as labeled fallback, not fake auto-posting |
| Public/private UI mismatch | Ship clearly proposed dashboard; refine from authorized references later |
| Cheap model produces weak content | Evaluation, lower cadence, better facts and quality-tier upgrade |

| Owner expects guaranteed rankings | Transparent metrics and product promise tied to work/measurement |

```text

base Maps cost = requests × mode price × applicable multipliers
```

These examples use four scans/month for easy budgeting; a weekly annual schedule averages 4.33, so budget approximately 8.3% more if running every week. They exclude failures/retries, extra result depth and other endpoints.

| 20 keywords × 7×7 × 4 | 3,920 | $2.352 | $7.84 |
| 20 keywords × 7×7 × 30 daily | 29,400 | $17.64 | $58.80 |

At 100 locations, the final daily Live example costs $5,880/month in base Maps requests alone. Unlimited daily large grids can destroy an inexpensive subscription's margin.

## 4. Text and image calculation

Illustrative eight-article monthly workflow, counting all drafting/checking/repurposing calls together:

```text
input = 200,000 tokens / month / location
output including billable thinking = 100,000 tokens
economy text base = 0.2 × $0.25 + 0.1 × $1.50 = $0.20
16 new 1K economy images = 16 × $0.0336 = $0.5376
```

This is a narrow inference-cost illustration, not a total content bill or a quality guarantee. Retrieval, grounding/search queries, quality-model escalation, rejected attempts, edits, image inputs and human review add cost. Budget **$1–4/location/month for text** and **$0.50–2 for limited images** initially, then replace estimates with observed p50/p95 cost per approved campaign. A premium model/content cadence can exceed those allowances.

Real owner photos and reusable branded templates are cheaper and often more credible than generating new photos for every post. Derive 1:1, 4:5 and 16:9 crops through deterministic image transforms. Add text/logo overlays with a renderer, not a new generation call. Never label a generated sample as a photo of completed customer work.

# Local SEO intelligence, competitor research and reputation specification

Added 28 October 2026. This expands the original blueprint. All scoring systems, schedules, thresholds and automation rules below are proposed product designs, not disclosed Google ranking formulas. This document is also embedded in the complete TXT handoff.

## 1. What intelligent operation means

The software should run an evidence-to-action cycle, not generate generic advice repeatedly:

Collect authorized observations → resolve business identity → validate freshness and completeness → detect a specific gap → identify plausible explanations → choose a bounded action → check consent/cost/risk → create or execute work → verify execution → observe later outcomes → retain, revise or stop the tactic.

For every recommendation answer: What did we observe? Where and when? What is missing? Why might this matter? What will change? Who approves? What will it cost? How will successful execution be checked? When will we evaluate outcomes? What else could explain the result?

Example: a plumbing business has a genuine emergency-callout service, but its page does not mention availability or the booking destination. The engine detects the mismatch from confirmed facts and the crawl, proposes a useful service-page edit, obtains approval, publishes a revision, verifies the HTML and booking link, then compares later matched-period search and enquiry observations. It must not claim that adding a keyword guarantees ranking gains.

## 2. Evidence and intelligence architecture

Add modules `local-intelligence`, `competitors`, `reputation`, `recommendations` and `experiments` inside the existing monolith. They call the existing facts, jobs, permissions, integrations and metering services. Do not introduce a new microservice or autonomous agent platform for each module.

New data structures:

- `evidence_records`: organization/location, subject, source class, source resource, observed time, coverage, uncertainty, permitted purpose, expiry, integrity hash and current availability.
- `entity_matches`: target/provider identity, confidence components, disambiguation reason and owner confirmation.
- `competitor_sets`: location, query cluster, grid/config version, entity membership and owner exclusions.
- `comparison_observations`: dimension, comparable sample, observation date and source-specific expiry; no universal permanent history.
- `recommendations`: rule version, evidence references, action, prerequisites, priority, cost estimate, risk, confidence, expiry, owner decision and suppression reason.
- `recommendation_runs`: input fingerprint, model/rule version, evidence coverage and output deduplication.
- `action_plans`, `action_dependencies`, `action_outcomes`: selected work, prerequisites, execution/measurement states and responsible actor.
- `review_resources`: authorized external reference, source revision, rating/text/reply cache, fetched time and expiry.
- `review_assessments`: ephemeral classifications tied to the source revision; do not use them to evade source storage restrictions.
- `review_reply_drafts`, `reply_approvals`, `reply_attempts`: owner-authored response, source revision hash, consent scope, publication/reconciliation state.
- `review_request_events`: transaction reference, eligibility basis, consent/suppression, delivery state and event deduplication; avoid unnecessary customer data.
- `experiments`: hypothesis, intervention, exposure window, baseline, matching rules, confounders and conclusion confidence.

Store expiring source payloads separately from long-lived owner decisions. A numeric vector, sentiment label or summary derived from restricted content does not automatically escape provider rules. Recommendations expire or lose their evidence links when the underlying data is no longer available. Validate retention and aggregation rights before enabling historical competitor/review dashboards.

### Evidence contract

```json
{
  "subject": "location:example/service:emergency-plumbing",
  "observation": "confirmed service absent from current service page",
  "sourceClass": "owner_facts_and_authorized_site_crawl",
  "observedAt": "2026-10-28T05:00:00Z",
  "coverage": { "pagesChecked": 12, "pagesExpected": 12 },
  "confidence": "high",
  "limitations": ["does not establish Google's ranking cause"],
  "expiresAt": "2026-11-04T05:00:00Z"
}
```

The dates above are illustrative fixture data. Production expiry comes from source policy and freshness configuration.

## 3. Local SEO operating pillars

### A. Accurate business identity

Normalize but preserve original business name, address components, public phone and website. Compare formatting separately from real disagreement: `Road` versus `Rd` need not be an address conflict. Recognize moved locations, departments, practitioners, franchises, hidden-address businesses and genuinely distinct branches. Avoid merging businesses solely by similar names.

The authoritative record contains service availability and exclusions, real-world name, operating/holiday hours, service coverage, booking destination and category evidence. Never invent a physical branch to target a neighborhood. Present identity/category edits as proposals with reasons and owner approval. Google's representation guidance requires accurate real-world business details. [S3]

### B. Search demand and commercial intent

Build keyword families from service, modifier, locality, language and intent: `AC repair`, `AC repair Indiranagar`, `AC repair open Sunday`, `AC repair cost`, and equivalent validated local-language expressions. Distinguish an implied-location query from a query containing a city name.

Use measured demand when available; mark unavailable values as unavailable. Separate branded/nonbranded terms and business-name queries from service discovery. Estimate service relevance from confirmed facts. A high-volume irrelevant keyword is not a useful opportunity.

### C. Geographic visibility

Keep organic website results, Maps grid results, local-pack observations and GBP activity distinct. Track request coordinate, zoom/viewport parameters when applicable, query wording, language, device, depth and provider. Do not equate Maps results with a local-pack position without collecting the relevant result surface.

A heatmap tells where a business appeared in a sample. Compare compatible runs and show error points. Distance is a fundamental factor; poor performance far away does not prove a broken profile. Google's stated factors are relevance, distance and prominence/popularity, not the software's internal health score. [S1]

### D. Helpful website coverage

Map one primary intent to a suitable canonical page. Improve existing pages before generating competing ones. Service pages explain actual service, eligibility, process, coverage, hours, practical next steps and verified proof. Location pages require genuine location/service context and useful differences, not city-name swaps.

Use actual business photos, accessibility information, transport/parking details where relevant, verified case examples and booking links. Do not invent landmarks, work completed, response times, staff credentials or prices. Keep medical/legal/financial claims in a stricter approval workflow.

### E. Reputation and business operations

Reviews inform customer experience and owner action. Detect repeated concerns, create operational tasks and draft appropriate responses. Do not treat keyword-rich replies, posting frequency or image geotags as proven ranking levers. Show a service-quality opportunity separately from a technical SEO problem.

### F. Citations and legitimate authority

Prioritize accurate listings on directories that matter to the selected category/country. Distinguish live verified listings from submitted forms. Compare real identity disagreements; preserve private addresses. Suggest genuine local associations, suppliers, sponsorships or editorial resources with an owner task, without promising paid-link ranking benefits.

### G. Technical accessibility and conversion

Check indexability, correct canonical destination, sitemaps, status codes, internal links, speed samples and usable mobile contact actions. Verify booking/enquiry flow rather than stopping at an SEO score. An authenticated booking tool may need a manual check; a crawler cannot prove a completed appointment.

## 4. Competitor analysis in depth

### 4.1 Discover the right competitors

Use query-cluster and geography-specific competitor sets. A bakery may compete with different businesses for custom cakes and breakfast. Owner-entered competitors are a separate list from businesses repeatedly observed in search results. Directory domains and national publishers may be website-search competitors while not being local service competitors.

Discovery flow: select relevant queries → collect licensed result samples on the owner's chosen grid → extract stable business identities → resolve duplicates/branches → calculate repeated overlap → exclude irrelevant or out-of-area matches → ask owner to confirm ambiguous entities → retain the source and expiry.

Never use owner-authorized GBP account APIs as a general competitor lead-generation database. Competitor observations must come from a source licensed for that purpose. No login-gated scraping or unbounded crawling.

### 4.2 Comparison dimensions

For each dimension show `measured`, `partially observed`, `owner supplied` or `unavailable`:

- Overlap by service/query/location and observed top-3 presence.
- Genuine categories/services/hours where licensed data exists.
- Provider-reported rating/count, date and sampling limitations.
- Review themes from a permitted sample, with sample size and window.
- Existing service/area pages and content usefulness on authorized public pages.
- Visible booking/contact journeys and mobile usability samples.
- Technical page observations and relevant publicly discoverable citations.
- Content update observations only when a reliable date exists; never infer a publishing date from a crawler visit.
- Backlinks only from an appropriate licensed data source; `Domain Rating` is not a Google metric and cannot be fabricated internally.

### 4.3 Explainable competitor opportunity

Do not conclude 'competitor ranks higher because it has more reviews'. That is correlation with many confounders. A good recommendation is: 'Three comparable observed competitors explain emergency availability clearly; your confirmed emergency service is missing from your service page. Improve that page and verify the outcome.'

Opportunity card includes evidence coverage, geography, comparable competitors, exact gap, confidence, estimated effort, action dependencies, owner approval and outcome measurement. Provide at most a manageable shortlist, such as five prioritized actions/week, rather than 100 repetitive suggestions.

### 4.4 Metrics and safeguards

Weighted top-3 coverage = sum of owner-selected keyword weights at successful comparable top-3 points divided by sum of weights at all successful comparable points. Weights express business importance, not Google ranking weight. Show denominator and missing coverage.

Competitor overlap = shared query-point appearances divided by relevant successful query-point samples under an explicit definition. Never label it total market share.

Review comparison uses the same available date window/source where possible. An API exposing only a sample cannot support a claim about all review themes. A sudden increase is an anomaly for investigation, not proof of fake reviews.

## 5. Recommendation engine and controlled execution

Use deterministic detection first, AI explanation second. Detection rules identify a broken booking link, conflicting holiday hours, missing confirmed service page, stale facts in a draft, declining compatible scan coverage, or an unanswered review. AI can group and explain evidence; it cannot invent missing measurements.

Proposed priority, with each input on 0–1 scale:

`priority = 100 × confidence × (0.30 customerImpact + 0.25 businessRelevance + 0.20 observedGap + 0.15 urgency + 0.10 strategicFit) / (1 + 0.5 effort + 0.5 incrementalCost)`

Risk, consent and source validity are hard eligibility gates outside this score. Score is an internal ordering heuristic, not a statistical probability of ranking improvement. Unknown inputs remain visible; avoid mechanically treating missing measurements as zero business value. Store the rule version and reasons.

Dependencies: confirm holiday hours before publishing an opening-hours update; fix robots blockage before creating additional SEO content; resolve location identity before sending review requests; obtain real case-study evidence before generating a case-study page. Collapse duplicate recommendations by location, action target, evidence fingerprint and cooldown.

Action lifecycle: candidate → evidence_ready → proposed → approved/policy_eligible → executing → execution_verified → observing → inconclusive/improved/worsened → retained/rolled_back/closed. Technical publication success is separate from business impact.

Run experiments conservatively. Record other concurrent changes, seasonality, holidays, outages and search updates. Prefer matched day-of-week windows and enough observations; expose uncertainty. A before/after chart does not establish causal lift. No repeated automatic rewriting every time rankings fluctuate.

## 6. Review system: end-to-end workflow

### 6.1 Scope and ingestion

Launch with authorized Google reviews; add other providers only after verifying their current APIs and permissions. Facebook recommendations, Instagram comments, private messages and website feedback are different resource types and must not be presented as interchangeable star reviews.

Use a bounded initial sync with pagination, stable IDs, update timestamps and source expiry. Google documents Cloud Pub/Sub-based notifications for supported profile events; implement authenticated delivery and periodic reconciliation so dropped/out-of-order notifications do not lose work. [S4]

A notification is a signal to refresh the authorized current review, not trusted reply text. Deduplicate by resource/revision. Handle changed ratings/text, removed reviews, existing owner replies, connection loss and deleted accounts. Show freshness and sync health in the UI.

### 6.2 Review inbox

Filters: location, provider, rating, response state, sentiment/topic, risk, language, assignee and age. Separate `unanswered`, `draft`, `needs_approval`, `scheduled`, `sending`, `verified_replied`, `changed_since_review`, `unknown_outcome` and `no_longer_available`.

Drawer: source review, provider link, available public author name, rating, timestamps, existing reply, suggested draft, classification reasons, business facts used, permission status and activity. Redact unnecessary personal data from AI contexts and logs. Never merge anonymous reviewers into a CRM identity by guesswork.

### 6.3 Classification before drafting

Proposed schema: language, star rating, positive/mixed/negative/unclear sentiment, topics, factual questions, privacy indicators, threats/abuse flags, health/legal/safety/refund dispute flags, sarcasm uncertainty, existing-reply state, confidence and recommended handling.

Use text plus rating. A five-star review saying 'Great if you enjoy being scammed' is not a positive auto-reply candidate. A blank rating can receive an owner-approved generic template, but not an invented service-specific response. Review text is untrusted content and cannot authorize tools or override system instructions.

### 6.4 Reply policy modes

Modes: off; draft only; approve each reply; narrowly scoped automatic positive replies. Start every business in draft/review mode. Enabling automatic mode requires a business owner to review sample responses, select location/provider/action, choose eligibility/rate/delay limits and accept a recorded, revocable policy. Verify the actual implementation meets current Google requirements before enabling recurring writes. [S2]

Proposed automatic eligibility requires ALL: currently connected approved capability; specific current consent; unchanged source revision; no existing reply needing protection; 4–5 stars AND clearly positive uncomplicated text; non-sensitive business/context; supported language validated for this tenant; no risk/privacy/uncertainty flags; no promises/compensation; business facts current; spending/rate limits; duplicate and novelty checks passed.

Low confidence, contradictory sentiment, 1–3 stars, complaints at any rating, refund disputes, allegations, emergencies, legal/medical matters and owner-flagged topics go to human review. Star rating alone never permits a public response. Business-specific stricter policies can override the default.

### 6.5 Reply generation

Reply should be brief, natural, relevant, use the business's approved voice and preferably the review's validated language. It may acknowledge the reviewer's actual words without inventing a transaction or repeating sensitive details. Use a public business support contact only when useful. No keyword stuffing, repetitive city/service insertion, promotional deals, requests to remove a negative review or invented refunds.

Examples, all illustrative:

Positive review 'Friendly team and quick repair': 'Thank you for the kind feedback. We’re glad you had a good experience with the team.' Do not add an unverified repair type or timeline.

Mixed review 'Good work but a long wait': draft 'Thank you for your feedback. We’re glad you were pleased with the work, and we’d like to understand the wait you experienced. Please contact our team using the support details on our profile.' Owner checks any operational commitment before posting.

Sensitive complaint: create an internal case and a conservative draft for review. Do not confirm the person is a patient/client, reveal order details, accept legal liability or promise an outcome the system cannot authorize.

### 6.6 Safe delivery and races

Google documents listing/getting reviews and creating/updating/deleting the business's reply; deleting a reply does not delete the customer's review. Verify currently supported permissions and endpoint contracts before production. [S5]

At dispatch: reload policy/connection/current review, compare review and reply hashes, check for a manual provider-side reply, acquire per-review publication lease, and preserve a pending operation ID. If anything changed, pause for re-review. Use local compare-and-swap to coordinate workers; where a provider lacks conditional writes, acknowledge residual external races and minimize the read-to-write interval.

On timeout, fetch the provider reply and compare normalized content before retry. A successful HTTP write is followed by verification. Do not overwrite a different manual reply. Edits, deletion and replacement require explicit control; record what the software changed. Pause/revocation cancels unsent operations immediately.

Suggested initial limits: configurable 5–15 minute owner-edit window, maximum five automatic replies/day/location, digest of actions and a one-click pause. These are product defaults, not provider rules. An edit window prevents some mistakes; it does not replace consent.

### 6.7 Quality evaluation and rollout

Create at least 60 labeled review examples: praise, rating-only, mixed, sarcastic, multilingual/code-switched, competitor allegations, personal data, refund, health/safety, threatening, edited review, removed review, existing reply and prompt injection. Critical criterion: no sensitive/complaint case should be auto-published in the acceptance set. Zero errors on the test set is not a production guarantee; start with shadow mode and monitor real owner corrections.

Rollout: draft-only → 20 owner-reviewed replies → shadow eligibility decisions → opt-in limited auto mode → periodic sampling and policy review. Keep provider approval/retention dependencies visible. Do not silently enable automation after a subscription upgrade.

## 7. Review acquisition and service recovery

Offer a neutral Google review link/QR and optional transaction-triggered invitations. Apply the same objective eligibility rules regardless of expected satisfaction. Separate private service feedback from the public review link without routing only happy customers to Google. No rewards, fabricated reviews or pressure for specific text. [S6]

Eligibility examples: genuine completed service, valid contact/consent, not opted out, not a duplicate transaction, reasonable frequency cap. Define how cancelled/refunded transactions are treated by objective rules rather than selectively suppressing unhappy customers. Keep logs proving the rule applied uniformly.

Delivery adapters are disabled until the business authorizes the channel and the launch market's requirements are checked. Do not infer outreach permission from a public review or an imported phone number. Implement opt-out/suppression, idempotency, quiet hours and limited reminders. Customer-created reviews cannot be automatically linked back to a particular invitation unless the provider supplies a valid permitted basis; report clicks separately from verified new reviews.

Service recovery queue: recognize an operational issue, assign owner, record internal follow-up and mark resolved only on owner evidence. Do not ask for a better rating as a condition of resolving a complaint. Suspected policy violations generate an evidence packet and provider-reporting guidance, never a promised removal service.

## 8. Review analytics with honest methodology

Metrics: current provider rating/count, current unanswered count, response coverage in the accessible set, median response time for known events, owner edit/approval rate, automatic eligibility/rejection reasons, delivery/verification failures and permitted theme samples. Show sample sizes and unavailable timestamps.

Do not present sampled-review averages as the platform's official overall rating. Avoid long-term derived GBP review trends unless retention/aggregation use has been cleared. Expose the selected allowed observation window and its limitations.

An optional private arithmetic simulator can explain averages using owner-provided aggregate values: current average R across N reviews plus x hypothetical reviews at score s gives (R×N+s×x)/(N+x). Mark as mathematical illustration, not a target, prediction, invitation selection rule or instruction to obtain only high ratings. Do not derive a precise original star sum from a rounded public average.

Review insight example: 'Wait time appears in 7 of 24 accessible reviews in this window; owner review suggested.' This is a sample observation, not a claim about every customer or causal ranking explanation. A suspicious spike is flagged as an anomaly, not an accusation of fraud.

## 9. Website, schema and content additions

Add service/area coverage matrix, useful local content briefs, internal-link opportunities and crawl-diff detection. Verify visible page content agrees with generated JSON-LD. Use a stable entity @id, appropriate business subtype, accurate hours/contact details and verified links. Schema validity does not guarantee rich results. [S7]

Do not expose a hidden residential address simply to satisfy rich-result requirements. Keep honest public information; if required properties cannot appropriately be published, explain reduced eligibility rather than fabricating data.

Displaying a testimonial widget does not make a business eligible for self-serving review stars in Google Search. Keep testimonial display, rights/source requirements and review-rich-result eligibility separate. [S8]

Business updates should use confirmed photos/offers/events. Expire stale offers and show rejected posts as rejected. Maintain a calendar with campaign intent and channel variants, not forced daily posts with repeated generic text.

## 10. Operational schedules and cost controls

Proposed defaults, adjusted for volume and source terms:

- Review notifications: event-driven with bounded reconciliation; do not promise instant delivery.
- Review drafts: after a valid new/changed review; deduplicate by source revision.
- Facts/hours conflicts: lightweight daily checks where permitted; ask owner before changes.
- Rank scans: weekly small-grid baseline; owner estimates cost before extra scans.
- Competitor refresh: weekly sampled metrics, monthly broader page-gap analysis where licensed.
- Crawl: weekly bounded crawl plus checks after a published technical fix.
- Recommendations: weekly shortlist and event-driven urgent technical/customer issues; suppress duplicates.
- Content planning: monthly plan, weekly adjustment; no mass churn from daily rank noise.
- Retention cleanup: daily or more frequently to meet source expiry.
- Provider capability/policy audit: recurring owned engineering task before version deadlines.

Add unit budgets for review assessment/drafting, competitor evidence collection and AI explanations to the existing ledger. High-volume reviews and third-party review analysis can cost more than ordinary text generation because of data collection and support. Use cached lawful evidence, bounded samples and no paid model call when a deterministic rule suffices. New modules increase scope beyond the original basic beta; schedule 3–6 additional focused weeks for intelligence/reputation hardening, adjusted after spikes, without treating this as an approval-time guarantee.

## 11. Example owner journey

An AC service business in Bengaluru connects WordPress and an authorized GBP, confirms a hidden address, service coverage, Sunday hours and public contact. The baseline finds weak sampled visibility for repair queries in one nearby cluster. Competitor research identifies missing repair-cost/process information on the existing service page, not a need for 30 new city pages.

The weekly shortlist proposes: repair a broken booking link; clarify confirmed Sunday availability; expand the repair page with grounded FAQs; review two unanswered complaints; prepare one genuine local-directory correction. It prioritizes the broken customer journey over more articles.

The owner approves page changes and review drafts. Straightforward positive reviews remain in shadow mode until explicit opt-in. One five-star sarcastic complaint is held. The software verifies published HTML and replies, logs spend, and measures later search/enquiry observations without claiming a guaranteed ranking lift.

## 12. Acceptance conditions

Competitor comparisons share defined surfaces/geography/time windows or disclose differences; unavailable data is never invented. Every recommendation links to valid evidence, explains confidence, has a bounded next step and respects source expiry. Review automation cannot run on rating alone, stale consent, edited source, existing manual reply, sensitive content or an unsupported language. Duplicate/replayed events and ambiguous external outcomes do not cause blind reposts. Review acquisition is neutral and permission-aware. UI retains the existing light-orange design system and clearly distinguishes drafts, proposals, scheduled actions and verified public changes.

ILLUSTRATIVE SCRIPT: scripts/generate-image.mjs
Copy into the NEW repository only. Not executed against a paid API in this task.

// Illustrative Antigravity handoff utility. Requires @google/genai in the NEW project.
// Not run against a paid provider during preparation of this plan.
import { GoogleGenAI } from '@google/genai';
import { readFile, writeFile, mkdir } from 'node:fs/promises';
import path from 'node:path';

const args = process.argv.slice(2);
const value = (flag) => {
  const index = args.indexOf(flag);
  return index >= 0 ? args[index + 1] : undefined;
};
const promptFile = value('--prompt-file');
const outputFile = value('--out');
if (!promptFile || !outputFile || !process.env.GEMINI_API_KEY) {
  throw new Error('Set GEMINI_API_KEY and pass --prompt-file <file> --out <file>.');
}
const prompt = (await readFile(promptFile, 'utf8')).trim();
if (!prompt || prompt.length > 12000) throw new Error('Prompt must be 1–12000 characters.');
const client = new GoogleGenAI({ apiKey: process.env.GEMINI_API_KEY });
const response = await client.interactions.create({
  model: process.env.GEMINI_IMAGE_MODEL || 'gemini-nano-banana-2.1',
  input: prompt,
});
const generated = response.output_image;
if (!generated?.data) throw new Error('No image returned; inspect provider status without logging secrets.');
const destination = path.resolve(outputFile);
await mkdir(path.dirname(destination), { recursive: true });
// Preserve the provider MIME type: the output extension should match actual bytes.
const mime = generated.mime_type || 'image/png';
const extensions = { 'image/png': '.png', 'image/jpeg': '.jpg', 'image/webp': '.webp' };
const extension = extensions[mime];
if (!extension) throw new Error(`Unsupported output MIME type: ${mime}`);
const actualDestination = destination.replace(/\.[^/.\\]+$/, '') + extension;
await writeFile(actualDestination, Buffer.from(generated.data, 'base64'), { flag: 'wx' });
console.log(`Saved ${actualDestination}`);
